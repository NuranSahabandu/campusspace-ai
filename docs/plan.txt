 1. Executive summary
 Universities typically handle room and equipment bookings through email threads, paper forms and
 shared spreadsheets. That causes double bookings, rooms far too large or too small for an event,
 missing equipment on the day, damaged or lost items with no accountability, slow manual
 approvals and no data about how well spaces are actually used.
 CampusSpace AI replaces this with one integrated system:

  • Students, club representatives and lecturers use the Flutter app to browse rooms, submit
    a booking objective ("workshop for 45 people on 14 Nov, 2–5 PM, need PCs, a projector and 2
    wireless mics, budget LKR 8,000") and track its status.
  • Lab technicians use the Flutter app to hand equipment over and take it back, recording
    condition and a damage photo with the phone camera.
  • The ASP.NET Core API authenticates, validates and stores every request in PostgreSQL, then
    starts a LangGraph multi-agent workflow in an internal Python service.
  • A supervisor agent creates a structured plan and delegates to three specialist workers (venue
    matching, equipment allocation, policy and cost). Their result passes deterministic validation,
    then the graph pauses with interrupt() for human approval.
  • A Facilities Officer reviews the proposal, validation checklist and full agent trace in the React
    dashboard and approves, rejects or requests revision.
  • On approval, .NET confirms the booking and reserves equipment in one database transaction,
    protected by a PostgreSQL exclusion constraint that makes double booking impossible. The
    requester sees the result in Flutter and receives a confirmation email with a calendar invite.

  Design philosophy for ease of implementation: every non-trivial mechanism in this plan is copied
  from something you already built in the labs: the EF Core + JWT setup from Lab 04, the create_agent
  workers and Gemini client from Lab 05, interrupt()/resume and the checkpointer from Lab 06, and the
  supervisor, context isolation, evaluation harness and injection defences from Lab 07. Where a lecture
  suggests a heavier option than the lab, this plan uses the lab version and records the heavier option as
  a considered alternative in the ADR.

 In scope: rooms and their features, maintenance blackouts, portable equipment and loans, booking

 Out of scope (state this in the report): real payment processing (fees are quoted, not charged),
 integration with the university timetable system, recurring weekly bookings, and QR scanning

 7.1 Rules that keep the design safe and defensible
  1. Clients only call ASP.NET Core (/api/... with a JWT). This is the spec's mandatory backend
    rule.
  2. ASP.NET Core is the only caller of the agent service. Every request carries
    X-Service-Key; the Python service rejects anything without it.
  3. The agent service has no database credentials. Its tools call back into ASP.NET Core
    read-only internal endpoints (/internal/agent-tools/...) using a separate X-Agent-Key that
    only unlocks those GET/quote routes. The AI cannot create a booking, reserve equipment or send
    an email, even if tricked (Lecture 07: least privilege, limit the blast radius).
  4. ASP.NET Core persists the audit record. The graph's own checkpointer holds its internal
    state; .NET copies the trajectory, steps, tool calls, validation results and decisions into its tables,
    which React displays.
  5. The high-impact action is executed by .NET, only after an authorised officer approves,
    inside one database transaction.
  6. Long-running work is asynchronous (Lab 07 §8.3): .NET starts a run and gets 202 Accepted;
    a background service polls the run's status.

 8. Database design
 Target third normal form. Conventions from Lecture 04 and Lab 04: surrogate IDENTITY keys;
 natural identifiers (email, room code, asset tag) kept UNIQUE rather than primary; numeric(10,2)
 for money; timestamptz (UTC) for every timestamp; NOT NULL by default; CHECK constraints for
 business rules; FK columns indexed; ON DELETE RESTRICT by default and CASCADE only for
 children that are meaningless alone. EF Core's default PascalCase table names are fine (Lab 04
 uses them). Configure with the Fluent API in OnModelCreating or one
 IEntityTypeConfiguration<T> class per entity. Every business table has CreatedAt and
 UpdatedAt, set automatically in an overridden SaveChangesAsync.

 8.2 Double-booking prevention in the database
 Double booking is prevented by PostgreSQL itself, not only by code. Add this in a migration with
 migrationBuilder.Sql(...). If two officers approve clashing proposals at the same moment, one
 commit succeeds and the other fails with error 23P01, which the API maps to 409 Conflict.

 Migration SQL
 CREATE EXTENSION IF NOT EXISTS btree_gist;
 ALTER TABLE "Bookings" ADD CONSTRAINT no_room_overlap
   EXCLUDE USING gist ("RoomId" WITH =, "TimeRange" WITH &&)
   WHERE ("Status" IN ('Confirmed', 'CheckedIn'));




 8.3 Request status machine
 Booking request lifecycle (enforced by RequestStateMachine in .NET)




     Submitted              AgentProcessing              PendingApproval                  Approved                    Completed




                               AgentFailed                 RevisionRequested               Rejected                   Cancelled



 Revision: PendingApproval → RevisionRequested → graph re-plans → PendingApproval. Cancel allowed from Submitted/PendingApproval/Approved.

 10.5 Supervisor: plan once, follow in code
 Lab 07's supervisor asks the LLM for a Route after every report. Lab 07 Part 3 also measured that
 the team costs two to four times more than one agent. Because this workflow's stages are mostly
 known in advance, the supervisor makes one structured-output call to produce a Plan, then the
 dispatcher follows it in code. The LLM is called again only to re-plan (validation failure or officer
 revision). Record per-round LLM routing as the rejected alternative in ADR-3. This is also Lecture
 05's "least autonomy that solves the problem" and Lecture 07's "start simple" decision guide.

 Plan schema and routing
 from pydantic import BaseModel, Field

 class PlanStep(BaseModel):
     agent: Literal["venue_matching", "equipment_allocation", "policy_cost"]   # cannot invent a worker
     task: str = Field(description="One crisp instruction. Include IDs, not whole records.")

 class Plan(BaseModel):
     required_features: list[str]           # must be codes from list_feature_catalog
     equipment: list[dict]                  # [{type_code, quantity}] from list_equipment_catalog
     soft_preferences: list[str]
     steps: list[PlanStep]

 MAX_DELEGATIONS = 6

 def supervisor(state: State) -> dict:
     if not state["plan"] or state.get("replan_needed"):
         plan = planner_llm.with_structured_output(Plan).invoke(build_planner_messages(state))
         plan = enforce_plan_rules(plan, state["request"])   # code: venue first, policy last,
         return {"plan": [s.model_dump() for s in plan.steps],   # form fields override LLM
                 "requirements": plan.model_dump(exclude={"steps"}),
                 "step_index": 0, "replan_needed": False}
     return {}

 def route(state: State) -> str:
     if state["delegations"] >= MAX_DELEGATIONS:           # the cap lives in code (Lab 07 §4.3)
         return "safe_failure"
     if state["step_index"] >= len(state["plan"]):
         return "validate"
     return state["plan"][state["step_index"]]["agent"]


 enforce_plan_rules is deterministic: the plan must contain venue_matching, policy_cost must be
 last, equipment_allocation is removed when nothing was requested, and attendees, dates and
 budget always come from the form, never from the LLM. If planning fails twice, a fallback plan is
 built from the form fields alone and the trace records planner_fallback: true.


 10.6 Workers and the isolation boundary
 Workers are LangChain create_agent ReAct agents (Lab 05 Task 03, Lab 07 §3.1): the LLM decides
 which of its own tools to call and with what arguments. run_worker copies Lab 07 §3.2: it accepts
 only a task string and returns only the final result, so no conversation history leaks in and no tool
 debris leaks out.

 app/workers + graph nodes
 from langchain.agents import create_agent
 from langchain_core.messages import AIMessage

 venue_worker = create_agent(worker_llm, tools=[search_available_rooms, get_room_details],
                             system_prompt=VENUE_PROMPT, response_format=VenueResult)
 WORKERS = {"venue_matching": venue_worker, "equipment_allocation": equipment_worker,
            "policy_cost": policy_worker}

 def run_worker(name: str, task: str) -> dict:
     """ONE worker, ONE task string. Returns only the structured result (context isolation)."""
     result = WORKERS[name].invoke({"messages": [{"role": "user", "content": task}]},
                                   {"recursion_limit": 12})          # per-worker step cap
     return result["structured_response"].model_dump()

 def make_worker_node(name: str, state_key: str):
     def node(state: State) -> dict:
         task = state["plan"][state["step_index"]]["task"]          # task_, never messages
         out = run_worker(name, task)
         return {state_key: out,
                 "messages": [AIMessage(content=summarise(out), name=name)], # trajectory tag
                 "step_index": state["step_index"] + 1,
                 "delegations": state["delegations"] + 1}
     return node



  Check response_format / structured_response against the LangChain version you install (the labs pin
  versions in requirements.txt; reuse those pins). If it is not available, have the worker finish with a JSON
  report and validate it with VenueResult.model_validate_json(...); invalid output counts as a failed
  step and triggers a retry.



 10.7 Tools
 Tools are @tool functions (Lab 05 Task 02). The docstring is the interface the model reads, the type
 hints become the JSON schema, and errors are returned as strings so the model receives an
 observation instead of a crash (Lab 05 Task 04). Each tool validates its arguments before calling
 .NET, applies a 10-second timeout and records itself in the trace.

     args = RoomSearchArgs(min_capacity=min_capacity, features=features,

 def call_internal(method, path, **kw) -> str:
     try:

 10.9 Human approval with interrupt() and resume
 Copied from Lab 06 Part 5. interrupt() checkpoints the entire graph state and ends the run; hours
 may pass; resuming carries only the decision. The graph must be compiled with a checkpointer or
 interrupt() raises.

 Human gate
 from langgraph.types import Command, interrupt

 def human_gate(state: State) -> dict:
     # Nothing with side effects above this line: on resume the node re-runs from the top.
     decision = interrupt({
         "request_id": state["request"]["id"],
         "proposal": {"venue": state["venue"], "equipment": state["equipment"]},
         "quote": state["quote"], "validation": state["validation"],
         "summary": state["quote"]["officer_summary"],
     })
     return {"decision_": decision["decision"], "revision_notes": decision.get("notes", "")}

 def after_gate(state: State) -> str:
     return {"approve": "finalize", "revise": "supervisor", "reject": "rejected"}[state["decision_"]]

 # resume (called by FastAPI /workflows/{id}/resume, which only .NET can reach):
 GRAPH.invoke(Command(resume={"decision": "approve", "notes": ""}),
              {"configurable": {"thread_id": run_id}})


  • thread_id is the AgentRun UUID generated by .NET, never taken from a client (Lab 06 Exercise
    6.1: thread_id is an authorisation boundary).
  • finalize re-runs V02 and V08 through the read-only tools and returns status: completed with
    the final proposal. .NET then executes the booking transaction. If the transaction hits the
    exclusion constraint (23P01), .NET records the failure and the officer can request revision.
  • revise sets replan_needed and passes the officer's notes to the supervisor's next planning call,
    producing a new proposal and a new interrupt. RevisionNo increments.
  • Checkpointer: SqliteSaver when the agent service runs locally or on a persistent disk (Lab 06
    stretch goal 4, one line). If deployed on an ephemeral host (Render free), use LangGraph's
    Postgres checkpointer (package langgraph-checkpoint-postgres) pointed at Neon in a
    separate schema. Never InMemorySaver in the demo: a restart would silently lose paused
    approvals (Lab 06 Exercise 6.1b).

 15. Security design

 15.1 Authentication and authorization
  • Registration hashes passwords with BCrypt (Lab 04 Task 03); login verifies and issues a JWT with
    NameIdentifier, Email and Role claims, signed HS256 with a 256-bit key from configuration (Lab
    04 Task 04).
  • UseAuthentication() before UseAuthorization(); [Authorize(Roles = "...")] on every
    non-public action (default deny).
  • 401 for missing, invalid or expired tokens; 403 for authenticated users without permission (Lab
    04 Task 05 test table).
  • Object-level checks in services: requesters may only read and cancel their own requests (Lecture
    04: role checks alone cannot enforce ownership).


 15.2 Token lifetime and storage
 Baseline (Lab 04): one access token, 60–120 minutes. React keeps it in Zustand persisted to
 localStorage; Flutter keeps it in flutter_secure_storage. Document the XSS trade-off of localStorage
 in ADR and the viva.

 Stretch (Lecture 04), if a day is available: 15–30 minute access token in memory plus a
 rotating refresh token stored hashed in a RefreshTokens table, delivered to React as an HttpOnly,
 Secure, SameSite cookie; POST /api/auth/refresh and /logout; interceptors refresh once on

 Trajectory checks (Lab 07 TODO 4 pattern)
 def trajectory_checks(case: dict, result: dict) -> list[str]:
     exp, failures = case["expect"], []
     for w in exp.get("workers", []):
         if w not in result["workers_consulted"]:
             failures.append(f"never consulted {w!r}")
     if result["status"] != exp["status"]:
         failures.append(f"status {result['status']!r} != {exp['status']!r}")
     if "quote_total" in exp and result.get("quote_total") != exp["quote_total"]:
         failures.append(f"quote {result.get('quote_total')} != {exp['quote_total']}")
     if "allowed_room_codes" in exp and result.get("room_code") not in exp["allowed_room_codes"]:
         failures.append(f"unexpected room {result.get('room_code')!r}")
     if result["delegations"] > MAX_DELEGATIONS:
         failures.append(f"runaway: {result['delegations']} delegations")
     return failures

 def build_graph(checkpointer):
     g = StateGraph(State)
     g.add_node("supervisor", supervisor)
     g.add_node("venue_matching", make_worker_node("venue_matching", "venue"))
     g.add_node("equipment_allocation", make_worker_node("equipment_allocation", "equipment"))

     g.add_node("safe_failure", safe_failure)
     g.add_edge(START, "supervisor")
     g.add_conditional_edges("supervisor", route, {
         "venue_matching": "venue_matching", "equipment_allocation": "equipment_allocation",
         "policy_cost": "policy_cost", "validate": "validate", "safe_failure": "safe_failure"})
     for w in ("venue_matching", "equipment_allocation", "policy_cost"):
         g.add_edge(w, "supervisor")             # every report returns to the hub
     g.add_conditional_edges("validate", after_validate,
                             {"pass": "human_gate", "replan": "supervisor", "fail": "safe_failure"})
     g.add_conditional_edges("human_gate", after_gate,

     for n in ("finalize", "rejected", "safe_failure"):
         g.add_edge(n, END)
     return g.compile(checkpointer=checkpointer)
